# 播放缓冲与低带宽排查（2026-11-06）

## 线上证据

- 实际听歌站为 https://music.tea-kompeito.com，排查时 healthz 版本为 redesign-b7ff83c，音乐源 wy。
- 浏览器直接向 m10.music.126.net 请求音频，响应 206、Accept-Ranges: bytes。音频没有经过网站服务器转发；当前架构已经是各自直连音源、WebSocket 同步房间状态。
- 发现每隔约 5 秒重复跳回相同时间：一次采样中缓存目标为 0.996 秒，服务器时间轴实际已到 56.711 秒，本地音频仍在 5.675 秒附近。
- 根因是 Pinia getter 内调用 Date.now()；时间本身不是响应式依赖，getter 缓存了旧时间。定时同步读取同一个旧值，反复 seek，触发 waiting / seeking。
- 在独立诊断浏览器中用实时目标时间替换同步函数：12.017 秒内音频从 85.453 秒前进到 97.410 秒，实际目标 97.471 秒；除第一次校准外无再次跳转。此验证只修改诊断浏览器，没有修改服务器。

## 修复

每次校准实时计算目标位置。已有跳转尚未完成、或正在缺少数据时不反复校准。加载元数据和用户主动恢复时仍允许立即定位到房间时间。

媒体请求失败后重新 load 再播放，最多两次退避重试；更换歌曲后取消旧重试。只有 NotAllowedError 显示浏览器播放授权提示，AbortError 不误报。相同歌曲换了播放地址时也重新载入。

## 带宽方案

| 流量 | 建议 |
| --- | --- |
| 音频 | 保持浏览器直接连接网易云 CDN，不改成由 1 Mbps 原站转发。 |
| 房间、聊天、进度 | 保留小体积 HTTP / WebSocket 状态同步。 |
| JS、CSS | 开启 nginx gzip，保留带内容哈希资源的长期缓存。配置示例已补充。 |
| 插画和其他静态资源 | 需要进一步改善多人首次打开速度时，可单独接静态 CDN。 |

排查时主 JS 约 116.8 KB，未开启 Content-Encoding；Vite 的 gzip 体积约 46 KB。WebP 主视觉约 108.7 KB，已压缩。静态 CDN 可改善首次加载，无法修复播放器内部的周期性回跳。

如果真的由原站转发音频，1 Mbps 在不计其他开销时，320 kbps 约容纳 3 路、128 kbps 约容纳 7 路；当前浏览器直连架构没有这一原站音频出口限制。不同用户到音乐 CDN 的网络质量仍需按修复后实际播放情况判断。

## 发布

本地修复和诊断浏览器验证不等于线上已发布。部署必须重新构建 Vite，执行 scripts/copy-dist.mjs，再重建并替换 musicd；只更新源码不会改变旧二进制内嵌的前端。nginx gzip 修改需要在正式配置中应用并执行 nginx -t 后 reload。

## 验证结果

- Vue / TypeScript 检查通过，Vite 生产构建和 Go embed 资源拷贝完成。
- 9 项浏览器集成测试通过，包括连续播放跨越三个 5 秒校时周期、媒体请求 503 后自动重载。
- 另将浏览器下载速率限制为 125000 字节/秒（约 1 Mbps）、延迟设置为 120 ms，连续播放回归通过，覆盖 15.6 秒以上播放及三次校时。该测试验证单个客户端的限速播放，不代表原站最大并发容量。

## 线上实播补充：CDN 节点返回 403

完整替换后实播发现，部分 jdymusic 播放地址的 m704/m804 节点返回 403；同一签名路径在对应的 m701/m801 节点返回 206。不同码率及新版解析接口仍可能给出失败节点，所以单纯降码率不能解决这次节点问题。

播放器在媒体加载失败后，仅对 HTTPS、默认端口、明确匹配的网易云 jdymusic 节点切换等价节点。保留签名、路径和查询参数，沿用最多两次重试；其他域名及其他存储池不改写。仍是浏览器直接拉流，不通过本站代理。

新增浏览器测试模拟原节点 403、备用节点返回音频，验证播放恢复及签名路径不变。此项与其他九项回归检查均通过。正式部署版本为 buffering-cdn-fix，更新时完整替换并重启 musicd，nginx gzip 保留启用。
